# Building MCP Servers for Bodhion

> **Audience:** Developers who want to add new skills to Bodhion via the MCP (Model Context Protocol) integration layer.

---

## What is MCP and how does Bodhion use it?

MCP (Model Context Protocol) is an open standard for exposing tool-callable capabilities to AI models over HTTP. Bodhion v1.26+ supports MCP natively: every enabled MCP server's tools appear automatically in the model's tool-use context, with full RBAC, audit logging, per-user credentials, and rate limiting.

```
User message
    → Bodhion model router
        → tool list (from all enabled MCP servers, cached in Redis)
            → model selects a tool
                → Bodhion calls POST /mcp-endpoint with JSON args
                    → your server processes and returns JSON result
                        → Bodhion injects result into the conversation
```

The standard transport Bodhion uses is **Streamable HTTP** (the `streamablehttp_client` from the `mcp` Python package). Your server must speak this protocol.

---

## Minimum required protocol surface

To pass the Bodhion validator and work as a skill provider, your server must implement:

| Endpoint / behaviour | Requirement |
|---|---|
| `POST /` (MCP initialize) | Accept an MCP initialize request, return server info |
| `GET /` or `POST /` (list_tools) | Return a `ListToolsResult` with at least one tool |
| Tool call handler | Accept a `CallToolRequest`, return `CallToolResult` |
| Error shape | Set `isError: true` on `CallToolResult` for failures |
| inputSchema | Each tool must have `type: "object"` JSON Schema |

**You do not need to implement these endpoints manually** — use the official MCP SDK:

- **Python:** `mcp[cli]` via `FastMCP` — one decorator per tool
- **TypeScript:** `@modelcontextprotocol/sdk` — `McpServer` + `server.tool()`

The scaffold script generates a working server for both languages.

## Auth type options

Choose the auth type that matches your server's security model:

| `auth_type` | When to use | How credentials flow |
|---|---|---|
| `none` | Internal/trusted servers, bundled servers | No credentials sent |
| `bearer` | API-key protected services | Bodhion sends `Authorization: Bearer <key>` header |
| `oauth_2.1` | User-identity-sensitive services (Gmail, GitHub, etc.) | Bodhion handles OAuth PKCE flow; per-user tokens stored and refreshed |

Set the `auth_type` field in your `bodhion-manifest.json` and in the Add Server form when registering the server.

For `bearer` servers: admins set a shared key in the MCP Servers admin tab. Users can optionally override with their own personal key via Connected Services.

## Running the compatibility validator

Before submitting to the marketplace, validate your server locally:

```bash
# Step 1: start your server on port 8000 (via supergateway or natively)
npx supergateway --stdio 'python server.py' --port 8000 --host 0.0.0.0

# Step 2: in another terminal, run the validator
python scripts/validate-mcp-server.py --url http://localhost:8000

# With bearer auth:
python scripts/validate-mcp-server.py --url http://localhost:8000 \
    --header "Authorization: Bearer your-test-key"
```

The validator runs 4 check groups:

1. **Connection & handshake** — can Bodhion's client connect and initialise?
2. **Tool discovery** — does `list_tools()` return at least one tool?
3. **Schema validation** — do all tools have `name`, `description`, and a valid `inputSchema`?
4. **Error-response contract** — does the server use `isError: true` on failures?

Exit code 0 = all checks pass. Non-zero = print the failures and fix before submitting.

## Docker and supergateway

Bodhion's MCP client connects over **Streamable HTTP**, not stdio. If your MCP server uses stdio transport (as most SDK-based servers do by default), wrap it with `supergateway`:

```bash
npx supergateway --stdio 'python server.py' --port 8000 --host 0.0.0.0
```

Your `Dockerfile` (generated by the scaffolder) already includes this pattern:

```dockerfile
RUN npm install -g supergateway
CMD ["sh", "-c", "npx supergateway --stdio 'python server.py' --port 8000 --host 0.0.0.0"]
```

For Docker Compose integration with Bodhion, add your service to the `bodhion-net` network so Bodhion's backend can reach it by container name.

## Submitting to the Bodhion Marketplace

1. Fill in `bodhion-manifest.json` with accurate values for all fields.
2. Make sure your server is publicly reachable or host it alongside Bodhion.
3. Open a PR to the Bodhion repository, adding your entry to `backend/bodhion/static/mcp-registry/registry.json`.
4. The CI workflow will run the validator against your server URL. Fix any failures.
5. On merge, your server appears in the marketplace with a **community** badge.
6. After the Bodhion team runs extended validation, it may be upgraded to **verified**.

Full contribution instructions: [`backend/bodhion/static/mcp-registry/CONTRIBUTING.md`](../backend/bodhion/static/mcp-registry/CONTRIBUTING.md)

## Tool design guidelines

- **One tool, one purpose.** Prefer `list_emails` + `send_email` over a single `manage_emails` tool with a `mode` arg.
- **Descriptive names.** Use `snake_case`. The tool name is the primary signal the model uses to pick the right tool.
- **Rich descriptions.** The model reads the description to decide when to call the tool. Include what it does, what inputs it expects, and what it returns.
- **Tight inputSchema.** Mark required fields. Use `enum` for fixed-value fields. The model fills the schema — the tighter it is, the fewer hallucinated calls.
- **Never log sensitive inputs.** Bodhion truncates audit log entries, but your server should also avoid logging full email bodies, passwords, or OAuth tokens.
- **Return structured data.** Return JSON-serialisable objects where possible. Plain text is acceptable for simple responses.

## Environment variables reference

| Variable | Phase | Description |
|---|---|---|
| `MCP_REGISTRY_URL` | 5 | Override with a private registry URL |
| `ENABLE_BUNDLED_MCP_SERVERS` | 6 | Auto-register bundled Docker MCP servers |
| `MCP_HEALTH_CHECK_INTERVAL_SECONDS` | 7 | Health check polling interval (default 60 s) |
| `MCP_HEALTH_HISTORY_RETENTION_DAYS` | 7 | Health log retention (default 7 days) |
| `MCP_SERVER_DOWN_ALERT_THRESHOLD` | 7 | Consecutive failures before admin alert (default 3) |
